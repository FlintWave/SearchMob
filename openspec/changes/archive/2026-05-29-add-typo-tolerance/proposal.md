## Why

A slightly misspelled query (for example a mistyped actor name) returns only literal-spelling
matches and nothing about the intended subject. SearchMob is a metasearch client: it passes the query
verbatim to each upstream engine and the adapters keep only title/url/snippet, discarding the engines'
own "did you mean" / "showing results for X" correction. There is no on-device correction and no
re-search, so typos fail hard. This change adds typo and "similar sounding" tolerance while honoring
the privacy goals: no new outbound calls, on-device first, store-nothing by default.

## What Changes

- Capture the upstream engines' own spelling correction. Add an optional `correction` to a successful
  engine result and an open `parseCorrection(body)` hook on the HTTP adapter base (default none).
  Implement it for the HTML engines that expose it (DuckDuckGo, Mojeek). The aggregator collects the
  per-engine corrections and picks a consensus (most frequent; ties resolve to the first seen). This
  reuses the response already fetched, so it adds no network traffic.
- Add an on-device spelling/phonetic corrector (`org.searchmob.correct`). It tokenizes the query and,
  for each out-of-dictionary, length-gated term, gathers candidates by edit-distance similarity
  (Jaro-Winkler and Damerau-Levenshtein, which suit names) and by a Double Metaphone phonetic bucket
  (for "similar sounding" terms), ranks them by `frequency x similarity`, and only proposes a
  correction above a confidence threshold. It runs fully offline and never throws.
- The corrector's dictionary is a compact bundled asset (a free-licensed common-English frequency list
  plus a popular-names list), generated by a committed script for reproducibility, and is augmented at
  runtime by the user's own opt-in encrypted search history so it personalizes privately over time.
- Combine the two signals in the single search choke point (`MetaSearchResultProvider.search`): prefer
  the upstream consensus correction; otherwise use a high-confidence on-device suggestion. Expose the
  result as an optional `didYouMean` on the search response. When the original query returns zero
  results and confidence is high, the corrected query is searched automatically and the UI shows
  "Showing results for X" with a link back to the original; otherwise nothing is auto-rewritten.
- Surface `didYouMean` as a non-intrusive banner above the results in the in-app search screen and in
  the browser-facing results HTML; activating it re-runs the search with the corrected query.

## Impact

- Affected specs: new capability `query-correction`.
- Affected code: `engine/EngineAdapter.kt`, `engine/HttpEngineAdapter.kt`,
  `engine/adapters/DuckDuckGoAdapter.kt`, `engine/adapters/MojeekAdapter.kt`,
  `engine/aggregate/Aggregator.kt`, `engine/MetaSearchResultProvider.kt`, the server `SearchServer.kt`
  and its result contract, `ui/search/SearchViewModel.kt` and `SearchScreen.kt`; new
  `engine/correct/**`, `app/src/main/assets/dict/**`, a dictionary generation script under `tools/`,
  and version-catalog entries for kt-fuzzy (MIT) and Apache Commons Codec (Apache-2.0).
- No new Android permission; no new outbound network call (the corrector is offline and the upstream
  correction is parsed from the search response already fetched).
